A better compiler, and what modern methods could do for this model

Research concept and direction by Adam Barnett. Two questions, answered plainly: could a redesigned compiler (for example one that writes every word as a short base64 code) make the model more compact with more parameters, and which of the methods that have appeared in the last two years would make our model faster or smarter. Every claim about our own model is tied to a measurement in docs/RUN_LEDGER.md; claims about outside methods say where they come from and how sure they are.

Short answer 1 a base64 compiler cannot help, for a reason worth understanding Short answer 2 yes, six methods are worth testing; three are cheap

1. What a code is, and why its spelling does not matter

The compiler turns each word (or word piece) into a number between 0 and 8,191. That number is all the model ever sees. It is not written out as text inside the model: the number selects one row of a table (the embedding), and from then on the model works with that row's 256 or 640 values. So:

  • Writing code 5,263 as the base64 string BSP changes nothing inside the model. The row selected is the same row. The model's cost depends on how many codes a text becomes and how many rows and layers it has, not on how a code is spelled.
  • If the model read the base64 characters instead, each word would become two or three codes (64 characters can only name 64 things; 64 × 64 = 4,096 names takes two characters), so sequences would get two to three times longer and the model slower and worse. We measured this direction once already: bytes as codes gave 1,000 codes per KB against 283 for words, and was 8% worse.
  • On disk, our code files already use 2 bytes per code (about 43% smaller than the text). Base64 text would use about 2.2 characters per code: no saving there either.

The lesson from the first phase still holds. A lossless encoder cannot add information: the total surprise in a text is a property of the text. An encoder can only change three things: how many steps it takes to read the text (speed), whether the same thing always looks the same (stability), and what structure it exposes for free. Packing more text into one code (phrases) was tested and lost by 2.5-4%, because rarer codes are learned from fewer examples and hide the words inside them.

So where would "more compact, more parameters" come from?

From two real levers, neither of which is the spelling of codes:

LeverWhat it changesOur experienceModern form
Fewer codes per text, chosen wellSpeed and sequence lengthStatic phrase codes lost (2.5-4% worse). Words beat bytes by 8%.Learned, dynamic chunking: the model decides where chunks end by how predictable the text is (Byte Latent Transformer, Meta, December 2024; H-Net, 2025). Long chunks where text is easy, short ones where it is hard. Reported to match or beat a standard tokenizer at the same compute, with better handling of noise and rare words. This is the engineered version of the original compiler idea, and it is testable.
More parameters without more compute per codeCapacity at fixed speedOur hashed tables (34M-537M parameters) helped 3-5% at 0.8M; exact count tables helped 10% at 0.8M and nothing at 5M+.Mixture of experts (only a few of many expert blocks run per code) and memory layers (a trainable key-value table consulted by the network; Meta, December 2024). Both add parameters that cost memory, not compute. Our tables were the untrained version of a memory layer.

A better compiler, if we engineered one, would therefore be: a dynamic chunker that keeps stable word keys for memory (our compiler's one real asset) but groups predictable runs into single steps, trained end to end with the model. That is a research item (section 4, test 5), not a change to how codes are spelled.

5. My view

  • The compiler is not where the gains are. Changing how codes are spelled does nothing; the measured value of the compiler is stable word keys for memory. The one compiler idea with modern evidence behind it is learned dynamic chunking (test 5), and it is a medium-sized research project with an uncertain payoff for memory keys.
  • Our training is a 2020 recipe, and that is the cheapest thing to fix. Tests 1-3 are an afternoon each on the 5M core and could together be worth 5-10% on every number we track. They should run before the next 50M run so that run uses the better recipe.
  • "Far more parameters at the same speed" is a real goal with two proven routes, mixture of experts and memory layers (tests 6 and 8). Both fit this machine at 50M compute. Memory layers are closest to what this research is about: a trainable store beside the network.
  • Speed is an engineering debt, not a design flaw. The profile shows the 50M network needs about 9 ms per code; our loop spent 70 ms around it. Test 4 is the fix.
  • Reasoning will come from practice and size, not equations. Verified self-training is the method behind 2025's reasoning models and already moves our numbers; a better-trained, larger core multiplies it.

Proposed order: 4 (so every later test runs faster), then 1-3 on the 5M core, then the 50M run again with the winners, then 6 and 8.
