The current model · C2b · 20 October 2026

C2b: how it was built, and how to add more reasoning

C2b is round 5's recipe plus training on messages with several parts, answered with two search options: question splitting (one search per question) and the two-hop search (a stored fact reached through something the user said). Against round 5 it won 5 fronts and lost 2 small ones; Adam adopted it as the strongest model. This section records exactly how it was made, the methods that held up over 13 runs, and how to add or strengthen reasoning skills.

Methods that held up

One chat stage from a pre-trained core, every kind trained together (stacked stages fade earlier skills). Training windows built by the same code that builds the answering window. A held-out plateau stop with a step floor. Decisions by the full suite plus the new tests, front by front at 2 standard errors, never by the training curve. A second seed for close calls. Every new ability as a switch that leaves older recipes byte-identical (checked on 320 windows each time).

What the last 13 runs taught

Retrieval first: the model can only use what reaches its window; two abilities needed a search change before training could help. Dose: a skill learned to 100% at 30% of its host kind still cost other skills; start low. Form: the target must come from the right source; windows whose answer always came from a stored fact taught the model to prefer stored facts over the conversation. Attribution: combine pieces only after each is clean, and read the answers behind a lost front.

How to add a new reasoning skill

  1. Write the test first (chat22/tests/suite_v2.py): held-out wordings, test-reserved names, the store's test split; run it on the best model for a baseline. A skill nobody tested cannot be judged.
  2. Check retrieval: print what reaches the window (the reply info's items). If the needed facts are missing, add an answer-time search option (off by default) and judge it on the best's seeds with no training, as hop2 and split were.
  3. Build a training switch (chat22/windows_train.py): windows in the answering layout; the target copied from the right source (a told turn, a stored fact, or both joined); "I don't have that" only when the information is truly absent from window and memory; wordings other than the test's. Verify byte-identity for old recipes and run a smoke training.
  4. Choose a dose: 10-15% of the host kind first; raise only if the skill's own test stays low.
  5. Train seed 1 and read the losses: a lost front has a mechanism in the answers (wrong source, copied refusals, the newest value lost). Fix the form or the dose, not the test.
  6. Combine only clean pieces, then a second seed, then write the winner into recipes/BEST.json.

Strengthening a skill that exists

More varied wordings (new families, not more of the same templates); harder decoys (look-alike facts, near-miss names); combinations (the skill inside multi-part messages); longer distances (the fact far back in an any-length session); and size: the 100M generalizes from the same data where the 5M learns patterns (skills 92% on training-style questions vs 39-47% on new wordings).

Signs of interference to watch

Refusals rising (grounding "refused", wrong refusals of told facts): copyable refusal text or abstain targets with the answer present. Story questions falling: answers taken from stored facts over the conversation. Documents falling: recap or "first thing told" habits. Near-miss falling: facts of different people mixed. Story contradictions: several people's facts in one message.

Next skills, ready to build

Counting and recaps (switch reasoncr, queued as c4). Comparisons from told facts ("Who is older, my sister or my brother?"). Order in time ("What did I tell you before the trip?"). Store-to-store chains ("Who leads the country the Eiffel Tower is in?": a second hop inside the store). Pronouns across split questions. Clarifying questions (5%). Arithmetic over told facts with the calculator tool.

Continuing at 100M

docs/TRAIN_100M.md: the C2b recipe on the 109M core with positions scaled to 2,048 codes and gradient accumulation (measured 0.83 s per step, 11.5 GB); about 10-11 hours per seed on an RTX 3090; the same data bundle plus the core bundle.

Now · the combined 5M loop (v2.5) · 20 October 2026

Lining every missing ability up in one chat stage

The best model is round 5: variant A's recipe, real memory facts, and any-length practice conversations built on a pool of real facts plus invented personal facts (two seeds; 7 significant wins and no losses against A). New tests written on 20 October showed what it still cannot do at all: combine something you told it with a stored fact, count or summarize what you said, or handle a message with several questions. Adam's direction: line every missing ability up in one chat stage, loop the 5M to its best, then build the 100M from the final recipe. The model's purpose at this size is simple chat (a game character) and fast fact finding; harmful-request handling is left to a deterministic filter.

Why the search had to change first

The model can only use what reaches its window. "Who wrote my favorite song?" does not contain the song's name, so the stored fact was never found (0/48). A message with two questions was searched as one query: both stored facts reached the window 0/12 times. Two answer-time options fix retrieval: the two-hop search searches the store again with the words of what you said (41/48), and question splitting searches each question separately (10/12). The untrained model still answers only some of these, so training follows.

How every gain is kept

A candidate never trains on top of the previous model: it retrains the one chat stage from the same 5M core with the best recipe plus its additions (about 3 hours). It becomes the best only if no test falls beyond noise and at least one rises, on two seeds; its additions are then written into the recipe (recipes/BEST.json) so every later run carries them. Each new ability is a switch that leaves older recipes byte-identical, with its own test first.

c1: training now

The best recipe plus earlier correct refusals before answerable questions, told-fact-plus-stored-fact windows, and counting / first-told / recap windows. The short-recall share rises from 12% to 21% so the original recall practice keeps its windows. Tested with the two-hop search on.

c2: next

c1's result plus multi-part messages (several facts told at once, two asked at once, a known and an unknown, a statement with a question, quoted notes, two real stored facts at once) and round 6's told-skills lesson at half strength. Tested with question splitting and the two-hop search on.

Rounds 6 and 7: parked

Round 6 (sessions with all 51k Alpaca stored Q&A): told skills 39% → 51%, but documents in the window 41% → 31% and story contradictions 0.04. Round 7 (sessions with natural rewordings): no wins, near-miss skills lost. One change per round made each cause clear; combined runs now make the loop faster, and a lost front is fixed by adjusting that one piece.

Then the 100M, and why it waits

A wasted 100M run costs 30+ hours; a behaviour fix costs about 4 at 5M. The 100M (109M parameters, core trained at 1,024 codes) is built from the final recipe: gradient accumulation is ready, positions stretched to the 2,048 window, a short speed and memory run first. It should lift what the 5M learns only as patterns (skills 92% on training-style questions vs 39% on new wordings; clarifying 0% despite 10,410 examples). A 16k window comes later as a short extension stage.

Next training · the merged model (v2.4) · revised 17 October 2026

Merging every gain into one model, with real facts

v2.3 proved the memory design works at any length, but lost ground elsewhere. A morning of diagnosis found why, the first repair (variant A) became the best model we have, and the plan below merges what each specialised training type gives into one model. It follows the big labs' staged pipeline where the evidence says it pays, and skips what a 5M model cannot use. Permanent knowledge is real facts only; made-up material lives only where it belongs, in conversation memory.

What v2.3 and the repair runs showed

v2.3: memory at any length works

Recall of 30 planted facts stayed flat from 100 to 10,000 turns (22-25 of 30; best earlier model 15). With engine v2: 83-90%. Reply time stays at about 0.26 s at every length: length costs storage, not speed.

v2.3: what it lost, and why

Never told in the window fell 99% → 45-72%: the short-recall kind (in-window facts, 25% never told, 68% of its windows longer than 1,700 codes) was cut from 12% to 2%. Told facts were refused 72-81 times under every memory setting: 30% of the any-length windows end in "I don't have that". Neither the search engine nor the test settings caused the window losses (those tests run with memory off).

Variant A: the best model so far

v2.2's recipe plus any-length conversations at 12% and full-length documents. Best or tied-best on 26 of 39 test fronts (next: v2.1 seed 1 at 20). Memory on: one fact 87%, never told 98%, two-step 90%; window back to v2.2 (never told 99%); told skills 79/180; grounding 79% right, 10% invented, 1.3% wrong memory.

Still open after A

Documents 26-32% (v2.1: 80%; a loss since v2.2, not v2.3). Skill updates 7-9 of 40 under every setting (v2.2: 19): A says "I don't know" correctly 30/40 but refuses 38 told facts. Story consistency. Runs D, E (documents) and F (long windows) target these.

Engine v2 and the real-facts store

Engine v2 rules beat today's search on every memory line (two-step 84 → 96%, wrong values halved) at about 0.1 ms per search. Swapping the made-up stored pool for real Wikipedia facts raised two-step 78 → 84% and stored skills 42 → 61%. The judge (part 2) is not usable yet: at the strict bar it kept only 26% of right items.

Training lessons

Every kind was still improving when A stopped (26,400 steps): the stop needs a floor (now 20,000, patience 10). A cut kind fades even when its held-out loss looked finished. Plain text never improves in a chat stage; it only holds while it stays in the mix. One 5M run needs about 11 GB of GPU cache: one training at a time, with a hard memory cap.

The staged plan: three training stages, not five

Why one merged mix, not stacked stages

Every kind trained in the same run kept its gain; every kind cut or left out faded (v2.3). Stacking one skill after another would fade each earlier skill. The labs fine-tune on mixtures for the same reason and keep earlier data in the mix (replay).

Why a grounding stage

The remaining errors are a balance problem (refuse vs answer, old vs new value) that example answers alone have not fixed. Our tests grade answers automatically, so preference pairs need no human raters: the labs' stage 4, aimed at the goal that facts come from memory and are never invented.

Before committing: two cheap tests

(1) The doubled learning rate: same held-out score in 65% of the time, but its quick suite lost fluency (1.340 vs 1.309), conversations (88 vs 110/120) and memory (one fact 5 vs 8/12): rejected, the held-out score alone hid it. (2) Weight merging: every variant starts from the same core, so their weights can be averaged (A + the best document variant + F) in minutes. If the average keeps both gains it is a shortcut; if not, the merged mix is confirmed.

Why not all five stages

Mid-training is the window extension: a separate, costly step, only after the 16k study. Reinforcement learning for step-by-step reasoning has little room in 5M parameters; it waits for the 100M. Each stage is tested at 5M before the 100M.

Datasets: real facts for knowledge, made-up material only in conversation memory

Rule (Adam, 16-17 October): anything the model treats as lasting knowledge is a true fact about real things. Invented people, events and stories are fine inside a conversation (that is what conversation memory is for), so the skills, any-length and story-world kinds keep their invented content. Training data that works is not changed without a stated reason and approval.

Decisions for Adam

1 · Rebalance the any-length endings

Never-told endings 30% → 15%, replaced by corrections where the newest value must be given. A training-data change, proposed because it is the measured cause of refused told facts and lost updates.

2 · The grounding stage

Auto-graded preference pairs on top of the stage-2 winner, with the mix replayed so nothing fades.

3 · SQuAD for evidence reading

Real Wikipedia questions with their paragraphs, already on disk (no download): buried evidence and document reading from real text, and relief for the Q&A shortage. Earlier 5M tests answered SQuAD poorly without the paragraph (13%), so it is proposed only with its evidence.

What today taught us, and how the next model is built

Today brought the first measured results from the clean chat22 package (v2.2) and from five sessions of measurements. Your direction (Adam, 16 October) is now standing policy: memory first (facts come from memory; the network reads, reasons and writes), any-length conversation is the main open question, the 8k window study is dropped (a 16k+ study comes later), and no 100M training until the 5M study is complete and the models work as intended.

Today's evidence

v2.1 on two seeds: not adopted

Long-context gains repeated (two-step 2% → 85%, never told 1% → 96-99%, document 50% → 70%), but recall from memory at 40 turns fell to 5 and 4 of 15 (arm A 14). The model retrieved the right fact and answered "I don't have that": its training paired facts in memory with "never told" targets too often.

Three audits

Every chat model since 15 October trained on 15 MB of plain text, not 300 MB. The new layout would have put the old value nearest the message. Some rules applied only when answering. Several tests could be passed the wrong way (always abstaining, naming both values). All fixed in chat22 and its suite.

v2.2 on two seeds: real gains, one big loss

Best of every chat model on clean text (wiki 1.321), told facts (37-38% vs 18-22%), in-window reasoning (never told 99-100%) and recall at 1,000-10,000 turns. But with memory on it dropped 20-40 points: the engine filled every memory block with six look-alike stored facts, and the model copied them ("Pablo is a large oil painting").

Each model is good at the format it trained on

v2.2: facts told in conversation 37-38%, stored 39-42%. Earlier models: told 18-22%, stored 62%. Training must cover both forms, and must look like what the engine really delivers.

Memory scales; the window has a cost

A fact told in turn 1 was still recalled 10 of 10 times after 5,000 turns (7.2M characters in memory), with a lookup of 18.7 ms. The window's attention cache belongs on the GPU (RAM is 2-5x and the NVMe drive 4-31x slower per code); big knowledge belongs in memory.

Memory-only side test

With the conversation window removed, single facts and abstentions mostly held, but two-step and corrections collapsed: the old search returns the top 3 matches, with no linked facts and no "newest" label. Arm A said "I don't know" correctly 11/12 times from a short memory-only input, against 0/12 with a long window of filler: a short, clean input keeps a small model grounded.

Step 1 (running): cleaner memory alone helps

On the strict setting, single fact with memory on went from 12 / 23 / 24 / 29 to 26 / 29 / 31 / 32 of 51 (512 to 4,096 codes), and stored-fact rewriting from 26 to 31/40, with no retraining. Final results (three settings, two seeds) set the v2.3 engine defaults.

The plateau trainer works

Both v2.2 seeds levelled off at the same step (19,000), cooled down and stopped at 22,800 instead of a fixed 30,000; the cool-down gave the largest single gain (0.609 → 0.565). The held-out set differed by seed, which is fixed for v2.3.

Limits (Adam, 16 October)

Training and tests on ultra-long context stop at 65,536 codes. Target window: 32k for the 5M, then 32k for the 100M if the 5M works well. Stress tests use at most 3/4 of the GPU and RAM. Disk tests only measure speed.

Why 32k

Measured in session 36: the 5M writes 14-16 ms per code up to 32k and re-reads a whole 32k window in 0.5 s; the 100M re-reads 16k in 0.4 s and 32k in 1.2 s. With the history cached between turns, each turn reads only the new text. Past 65k the wait grows quickly (5M at 262k: 55 s).

The window, v2.2

[older history … recent turns] kept in the cache, then [memory block] and [message] re-read each turn. The memory block takes every entry that applies from both memories, up to a quarter of the window: conversation pieces and notes, labelled by turn ("you said, turn 12"), and stored facts. The newest version of a fact wins, and two-step questions follow links.

Training for any length

The window keeps one shape whether the conversation is 10 turns or 10,000. A fact from turn 3 or turn 3,000 arrives the same way, as a memory item. So we train the skill, not a length: generated conversations of 10-10,000 turns, built with the engine's real search (including its misses), blocks of 0-40 items with 0-3 relevant. Success means a flat accuracy line from 100 to 10,000 turns.

Engineering before 8k / 32k

(1) The copy head scores every code against every code: at 32k that is 1 billion pairs per window, so it must be limited or chunked. (2) Each new code copies the whole attention cache; preallocate it. (3) Keep the history cached between turns and move the memory slot behind the history (v2.2 layout). (4) Positions past the trained window need rescaling (tested as an arm).

Long context: what we missed, and the plan to fix it

The guide's main point fits our results: a window is only room to store text. The model also has to be trained to find and use evidence wherever it sits. We already do several of its recommendations. The gaps below are the ones our own measurements show. We take what fits a 5M model with its own memory. Million-token windows, an outside teacher model and reinforcement learning stay out.

What we already do (keep)

  • Checked targets: every fact answer comes from our own generators or answer keys. Nothing comes from a teacher model.
  • Evidence labels: the gold spans and the intermediate-target loss (arm B) are the guide's "selected evidence" labels.
  • Regression guards: short tasks stay in the mix (rehearsal 20%, skills 25%), and the skills and probe tests are run on every arm.
  • Clean splits: splits by source, deduplicated and audited (the data audit below).
  • Runtime: answer-time tools for arithmetic and dates, the verifier, and session memory for facts that must stay consistent.

Risks, and where each would come from

Wait grows with the window

Reading the window is the cost before the first word; it grows with the conversation. Writing stays fast because of the KV cache, but each step also attends to the whole window.

Positions past 2,048

The core trained at 1,024, the stage at 2,048. Text past the trained window is untested ground: rotary positions continue, but the model has never seen them, so quality is expected to drop there.

Session memory misses

A scrolled-out detail comes back only if the lookup finds it. Rewording ("my sibling" for "my sister") can miss; this is the retrieval weakness K2 is meant to fix.

5M knowledge

Conversation and memory skills do not add general knowledge: without memory the 5M network still writes fluent nonsense (rated 7.9–9.9). Stories will be short and simple.

Long replies drift

Small models repeat and lose the thread over hundreds of codes. The repeat block (no 3-code phrase twice) helps; the story test measures the rest.

Mixing five kinds of data

Each share takes steps from the others. The chat probe and report card check that Q&A and language were not traded away.

The verifier is only as good as its check

It prefers answers whose words are found in the evidence. That catches "Jakarta" beside a Tokyo entry, but not a correct rewording that uses new words, and it multiplies the answer time by the number of candidates. Off for replies without evidence (stories, chat).

Self-training at 5M

Outcome-rewarded training worked at billions of weights; our one earlier try (math, 5M) gained 1.5 points. One round on the model's own correct answers may change little; D measures it.

Tools are narrow

The calculator reads "12 plus 30", "7 x 8" and "have three apples ... eat one"; anything worded otherwise falls back to the network. It ignores phone numbers, codes and times on purpose.

Streaming

Yes. Replies appear word by word in the terminal as they are written, in conversation mode. The last few characters are held back until the reply ends, so the stop markers never show. When the verifier checks several candidates (only when memory or a tool supplied evidence), the chosen reply appears word by word once the check is done, a fraction of a second later on the GPU. Stories and ordinary chat stream as they are written. The line under each reply shows how full the window is, how many turns it holds, whether an earlier turn was recalled from session memory, any tool used, and the first-word wait. Settings: CHAT_VERIFY (3 by default, 0 to turn off), CHAT_TOOLS, CHAT_REPLY_CODES.
