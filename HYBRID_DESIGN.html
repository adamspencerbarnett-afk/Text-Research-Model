The Hybrid Memory Model: a fast, lightweight chat system that keeps its knowledge outside its weights

Research concept and direction by Adam Barnett. This document takes what three weeks of measured results established, adds the parts of modern retrieval-augmented generation (RAG) that fix our measured weaknesses, and designs one system around them: a small network that reads, copies, reasons in steps and checks itself, over a memory it can search in microseconds and learn into at once. Each part is designed in the same loop: role, design, evidence from our runs, interfaces, failure modes, open research, and the measurement that decides it.

2. The system in one picture

A chat turn flows left to right. Memory and retrieval are cheap and run first; the network runs last and only for the words memory cannot supply. Two loops run outside the turn: write-back (facts and turns stored at once) and consolidation (what is used often is trained into the network's own memory layer during quiet time).

3. Each part, designed in the same loop

For every component: what it does, how it is built, the evidence that shaped it, its interface to the rest, how it fails, what is still open, and the measurement that decides it. Colours follow the picture: memory, judgement, network, dialogue.

3.1 Compiler and codes

Role
Turn text into codes and back without loss; give every word a stable key that memory can hash.
Design
Unchanged: the deterministic 8,192-entry dictionary with byte fallback, native C++ encoder, one dictionary per training mix, hashed for reproducibility.
Evidence
Within ±1% of a standard tokenizer on prediction; stable keys are what made the exact tier and the copy pointer simple. Phrase codes lost 2.5–4%; byte codes lost 8%.
Interface
encode(bytes) → codes, decode(codes) → bytes, key(question) → set of content words.
Failure modes
Digit runs split unpredictably (a number channel is a later, math-line item); dictionary drift between mixes breaks weight reuse, so the dictionary hash is checked at load.
Open research
Learned dynamic chunking (surprise-based boundaries) is the one compiler idea with modern evidence, and a medium project with uncertain payoff for keys. Not before the core work.
Decides
Bits per byte at equal compute and reply speed; memory recall must not fall.

3.2 Memory tiers and the duplicate check

Role
Hold knowledge outside the weights in the cheapest store that is still correct for its kind.
Design
Five tiers. Exact: question–answer pairs keyed by content words, hashed; returns the stored answer verbatim. Passage: documents cut into 200–500-word chunks with a title and source, indexed lexically and densely; this is the RAG tier we lack. Session: the current conversation's turns, indexed the same way, cleared or archived at the end. Program: question patterns paired with small typed programs with slots, run by an exact executor (section 3.11); the calculator and date arithmetic are its first entries. Learned: a product-key memory layer inside the core (section 3.5), filled by consolidation. All five are searched by the same cascade.
Duplicate check
On every add: exact hash (µs); if no hit, the rarest two or three content words select candidates from the inverted index and only those are scored (ms); between 0.5 and 0.9 similarity, the model is asked the question and the pair is skipped if it already answers correctly. Conflicts (same question, different answer) replace the old entry and log it.
Evidence
Exact path 100%; taught facts 77% F1 after rewording; evidence shown to the core cuts its error 33–36%; count tables (an untrained memory layer) reversed with size, so the in-core tier must be trained.
Interface
add(kind, key_text, payload, source) → id | duplicate_of; candidates(query, k) → [(id, lexical, dense)]; get(id) → codes.
Failure modes
Stale facts (handled by conflict replacement and a timestamp); passages too long for the window (chunk at paragraph boundaries, 300 words target); session memory leaking across users (scoped by session id).
Open research
Chunk size against reading accuracy; whether a per-domain adapter (the "synapse" idea in BRAIN_DESIGN) beats a shared learned layer; forgetting policy for session memory.
Decides
Stored and added exact rates; SQuAD-style exact match from the passage tier; duplicate precision on a labelled set.

3.3 Retrieval cascade

Role
Find the right memory fast, and say how sure it is.
Design
Four stages, each only when the previous did not settle it. 1 Exact hash. 2 Hybrid search: inverted index over content words (IDF-weighted, as now) and a dense encoder, scores combined at a weight fitted on held-out rewordings (2.0 today); top 50 from each. 3 Reranker: a scorer trained on outcomes (did this candidate's answer help the answer?) orders the top 10; a small cross-encoder is the baseline to beat. Reranking by the core's own surprise at the question was measured and rejected (13 October). 4 Gate: a learned threshold on (lexical, dense, rerank) that decides whether to use the best match, use several, or none. The cascade returns the candidates with their scores; the trust head sees them.
Evidence
Literal 75.1% → hybrid 80.9% recall@1 on rewordings; retrieved answers 11–13% closer to the reference on reworded and new questions (session 21), adopted. The gate helped at 50M (21 → 24/32) and hurt at 5M (21 → 19/32), so it must be learned and size-aware. Query-likelihood reranking by the core improved retrieval on reworded questions (0.261 → 0.291) but worsened it on new ones (0.217 → 0.185) and lowered every answer score: rejected.
Interface
retrieve(query, history, k) → [(id, tier, lexical, dense, rerank)], latency budget 5 ms for stages 1–2, 20 ms with the reranker.
Failure modes
Dense encoder is an outside pretrained model (labelled in every result; an in-domain contrastive key is the replacement); reranker cost grows with k (cap at 10); the gate learned on one size misfires on another (train per size).
Open research
Train our own dense key on in-domain pairs; a reranker trained on answer outcomes; multi-hop: a second retrieval conditioned on the first result.
Decides
Recall@1 and @10 on rewordings; reworded and new-question F1 after the stage-2 model is trained on the new retriever.

3.4 Context builder

Role
Pack the window so the generator sees the right things in the right order, within a fixed code budget.
Design
Window layout: [recent turns, newest last] [evidence 1..k, each prefixed by a tier and confidence tag] [question] [thinking budget] [answer]. Evidence is ordered by rerank score with the best nearest the question (small models attend locally). The budget is 1,024 codes at 100M and 2,048 at 300M; turns are summarised by the session tier when they overflow.
Evidence
512 beat 256 on every Q&A group; a single retrieved exchange is the design today, and top-3 retrieval has been queued since early October without a run; the 50M core trained at 1,024.
Interface
build(turns, evidence, question, budget) → codes, span_masks, confidences; span masks tell the copy pointer where it may point.
Failure modes
Distractor evidence pulls the answer (fixed in training, 3.5); long histories crowd out evidence (summaries); the model copies the confidence tag text (tags are special codes, never decoded).
Open research
How many passages a 100–300M model can use before accuracy falls; whether tag codes carrying confidence beat feeding the scores to the trust head only.
Decides
Answer F1 against k; "lost in the middle" test with the gold passage at each position.

3.5 Generator core

Role
Read what it is given, write fluent language, and plan a few steps; it does not need to know facts.
Design
Shallow-wide Transformer, 100–300M parameters, modern block (RoPE, RMSNorm, SwiGLU), 6–8 layers, width 1,024–1,536, grouped-query attention for a small cache, tied embeddings, bf16 training, int8 weights at rest. A product-key memory layer after the middle block is the learned tier: 256k–1M entries with 128-wide values projected up to the width (33–130M parameters, int8 at rest; values at full width would be billions of parameters, so the value width is the lever). Multi-token prediction heads (2 extra) give draft codes for the decoder and a small planning gain. The copy pointer reuses the last layer's attention keys instead of its own projection (one fewer matrix product per code). Training recipe (sessions 20 and 22, two seeds): Muon for the block matrices with a warmup-stable-decay schedule, fused AdamW for the rest, bf16, resumable checkpoints. First point, prepared 13 October: 1,024 wide, 8 layers, 16 heads, 109M parameters, window 1,024, batch 32, on the P100 mix (3.3 GB: web, Wikipedia, books, conversation, evidence pairs, question pairs; no worked maths), 61,035 steps = 2 billion codes (about 20 per parameter), measured at 51,000 codes per second and 18.3 GB, so about 11 hours across one or two nights. Dictionary size is a research item: 16k–32k codes would shorten sequences by about 15–20% at a small embedding cost (11.1).
Evidence
Reading 1% → 28% from 5M to 50M; depth did not help and cost speed; modern block −1 to −7% on text; Muon + WSD −0.9% on text (two seeds); count tables reversed with size. None of the text gains reached answers at 5M: the generator's size is the next lever.
Interface
hidden(codes) → states, step(code, pos, cache) → logits, state; the mixer and decoder see only these.
Failure modes
Memorising the Q&A set in stage 2 (rehearsal of stage-1 text, 30%, as now); the learned layer hoarding frequent trivia (consolidation picks by use, with decay); undertrained at 300M on one GPU (WSD lets the run be resumed across nights).
Open research
The size at which reading becomes good (100M, 200M, 300M points, same recipe); memory layer entries against accuracy and speed; mixture of experts as the alternative "more parameters, same compute".
Decides
Report card (fluency, evidence gain, reword recall), SQuAD exact match from passages, chat probe, joules per answer.

3.6 Output mixer: the trust head

Role
For every code, choose between the network, the copy pointer, the learned memory and a tool, by how much each can be trusted right now.
Design
As today, a small head over the hidden state that outputs mixture weights over sources, extended with the retrieval scores (lexical, dense, rerank, gate decision) and the copy pointer's confidence. Retrieval confidence is always an input (13 October): every stage-2 run so far trained with that input switched off, so a wrong exchange and a reworded right one looked alike apart from their content, which is the likely reason the two training lessons cancelled at 5M. The program tier is a source whose "distribution" is a single code sequence: the executor's result, copied out in one draft. The mixer is trained jointly with the core on the stage-2 loss, so it learns when copying is right and when it is not. Training windows carry three kinds of bad evidence, a distractor, nothing, and two conflicting pieces with different confidence tags, so the head learns to prefer the better-tagged source and to fall back to the network.
Evidence
The copy pointer is what lifted 13% to 89%; trained also on the right answer under a reworded question it reached probe 24 and 23/32 (two seeds) with reworded questions 5/5 and 4/5; misleading evidence raised the network alone 20%. The leave-one-out trust head over count tables gave 9–11% at 5M and was dropped at 20M, so the head itself works and the sources must be the right ones.
Interface
mix(state, sources, confidences) → log-probabilities over codes.
Failure modes
Over-copying from a wrong match (distractor training in 3.5 and the gate); mixing probabilities in bf16 (the mixer runs in fp32, as now).
Open research
Whether a per-position mixture beats a per-answer "mode" decision; adding the support-check signal as a source weight.
Decides
Stored and added exact rates with and without each source; wrong-evidence test (gold replaced by a distractor) must not fall below the network-alone score.

3.7 Decoder: one graph replay per code, several codes when copying

Role
Make answering as fast as the hardware allows.
Design
CUDA graph step (built, 12 October): fixed-size buffers for the window, attention cache and copy keys; one launch per code; identical replies. Copy-as-draft: when the pointer is copying, the next k codes after its target are a draft, taken from anywhere in the window (the retrieved answer, a passage, an earlier turn); one batched replay verifies them and keeps the longest agreeing prefix (prompt-lookup decoding, strongest exactly on evidence-copying answers). The multi-token heads supply drafts when nothing matches; a program result is one draft. Evidence cache: every passage's attention keys and values are computed once and stored unrotated; the rotary rotation is applied at attention time by the evidence's slot in the window, so cached states are position-independent and prefill covers only the question and history. Without this, prefill dominates at 1–2k-code windows. Early stop: the support check runs inside the loop as a running count of unsupported content words, so a failing answer stops early. Precision: bf16 weights (identical to fp32), int8 at rest; compute in fp32 inside the graph because low-bit kernels were slower at these sizes.
Evidence
11.7 → 1.75 ms per code at 5M, 14.6 → 3.6 at 50M; low-bit kernels 1.4–4x slower and altered replies; the GPU is launch-bound below ~300M.
Interface
answer(context, max_codes, draft_source) → codes, with the per-code mixer called inside the graph.
Failure modes
Answers past the window (fall back to the eager loop); drafts verified in a different numeric path than single steps (verify with the same graph shape, batch of k); graphs captured per window size (one per budget).
Open research
Draft length k against acceptance rate; at 300M, whether bf16 compute inside the graph finally pays (bandwidth-bound regime begins).
Decides
ms per code and joules per answer on an idle GPU, replies byte-identical to the eager loop.

3.8 Reasoning and dialogue: a chatbot, not a lookup

A lookup system returns what it finds. A chatbot has to follow the conversation, decide what it needs, think in steps and know when it is wrong. The research says a small network cannot do that from its weights alone (math stayed at 2–4% at every size and depth), so reasoning here is built from pieces that each work at small scale: memory of the conversation, retrieval the model can request, explicit thinking codes trained by verified practice, and a check before answering.

Dialogue state
The session tier holds every turn; the context builder always includes the last two turns verbatim and retrieves older ones by content, so "the second one" and "as I said earlier" have referents. Facts the user states ("my dog's name is Rex", "I have five apples") are added to the exact tier and, where they fit a pattern, to the program tier as typed state (entity, attribute, value), the September event row; "how many apples now?" is then a state query, executed exactly. Older history is summarised extractively (entity facts plus the last answers), never by generation, so summaries are free and verifiable.
Retrieval the model asks for
Interleaved retrieval: a special code SEARCH followed by a short query ends a thinking step; the engine runs the cascade, inserts the results, and generation continues. Multi-hop questions become two short searches instead of one impossible one, with a two-hop limit. Trained from traces built automatically from the evidence pairs (question → query → passage → answer) and from synthetic two-hop chains.
Thinking codes
A bounded scratch region before the answer (special THINK … END codes, never shown) in which the model writes the steps: restate what is asked, list what the evidence says, resolve references, decide. Small models gain from explicit steps because each step is a short, local prediction. The budget is small (64–128 codes) and cheap under the graph. Thinking is adaptive: exact hits, program answers and matches the gate marks confident skip it entirely, so most turns spend no thinking codes; only uncertain turns think. The loss on thinking codes comes only from verified traces, never from unverified ones, or the model learns to ramble.
How it is trained
Verified practice, the method that moved math 2.5% → 4.0% and the one behind current reasoning models, applied to text tasks with checkable answers: reading comprehension with exact-match answers (SQuAD, HotpotQA-style multi-hop), entity tracking in dialogue, consistency questions over the session ("what did I say my name was?"). The model samples thinking + answer; only traces whose answer the checker confirms are kept and trained on. Then preference tuning (DPO) on pairs of better and worse conversational answers for tone, staying on topic and stopping.
Self-check and refusal
The support check (3.9) runs on the draft answer; if unsupported, the model may search once more or answer "I don't know, the closest I have is …" with the nearest match. A chatbot that says this is more useful than one that guesses.
Open research
How much thinking a 100–300M model can use before it drifts; whether thinking traces should be retrievable (a worked pattern memory, the text version of the math template idea); interleaved search against single-shot top-k; the right checkers for conversational tasks.
Decides
Multi-turn probe (new section: reference resolution, consistency, follow-ups), multi-hop exact match, chat section of the probe, refusal precision (how often "I don't know" was right).

3.9 Support check and provenance

Role
Never state what nothing supports; show where an answer came from.
Design
For each content word of the draft answer, the trust head's source weights say whether it was copied (from which evidence id), produced by the network with what probability, or computed by a tool. An answer whose unsupported share exceeds a threshold is flagged; the engine then searches once more or returns a refusal with the nearest match. Replies carry source ids; the chat prints them, as the memory line does today.
Evidence
The memory path cannot hallucinate; the network path does (the 'graphics card' reply). The signals already exist in the mixer; this is the text version of the paused math check loop.
Interface
check(answer_codes, source_weights) → support_share, sources, verdict.
Failure modes
Fluent connective words counted as unsupported (only content words count); paraphrased copies missed (match on the dense key of the sentence, not only exact words); a slot copied into a program from the wrong entity gives a confident wrong answer (slot copies carry the pointer's confidence like any copy, and a low one blocks execution).
Open research
The support threshold is a placeholder: it is fitted per core size on a set with known-unanswerable questions; learning the verdict instead of thresholding.
Decides
Refusal precision and recall on a set with known-unanswerable questions; hallucination rate on new questions.

3.10 Learning that never stops

Role
Keep improving without retraining the whole model, and without forgetting.
Design
Write-back: every turn goes to the session tier; facts the user states go to the exact tier; answers confirmed by a checker or by the user go to the exact tier as new pairs, after the duplicate check. Practice: in idle time the model answers held-out questions from the passage tier, keeps verified traces, and fine-tunes the heads and adapters on them (STaR). Consolidation: entries used often are trained into the learned memory layer and per-domain adapters in a low-rate pass with rehearsal, so frequent knowledge becomes cheaper and the exact tier stays small. Forgetting: session entries expire; exact entries unused for long are archived, not deleted.
Evidence
Instant learning works (taught facts 77% F1); full fine-tunes on self-solutions cost copying of new facts (−18 points on added questions at 50M), which argues for adapters; a gentle core rate with rehearsal kept stage-1 gains.
Interface
learn.write_back(turn), learn.practise(budget_s), learn.consolidate(budget_s); all resumable and metered.
Failure modes
Learning a user's mistake (only checker- or user-confirmed answers are stored; conflicts logged); drift of the core (adapters and heads only, core frozen between planned retrains).
Open research
Adapter versus memory-layer consolidation; how much practice per night pays; when to retrain the core.
Decides
Added-fact accuracy after consolidation, stored accuracy must not fall, probe before and after a night of practice.

3.11 Program tier: exact execution of retrieved typed programs

The September system's strongest idea returns in the one form that fits an open-language chat: not a hand-written grammar, but programs stored in memory and found by retrieval. The network never computes; it chooses a pattern and fills its slots by copying, which is its proven strength, and an executor does the rest exactly.

Role
Give a small network exact multi-step results it cannot produce from its weights: counting, comparing, dates and durations, units, list operations, dialogue state ("I had five, gave two"), consistency against stored facts, and multi-hop queries over memory (find, filter, join). Arithmetic word problems join later, when the math line opens, through the same slot.
Design
An entry is (question pattern, typed program with slots, executor). Programs are V1's event rows generalised: a short list of typed operations over entities, attributes and values. At answer time the cascade retrieves candidate patterns like any other entry; the network fills each slot by pointing at a span in the question or evidence (the copy pointer, with its confidence); the executor runs the program on the CPU in microseconds; the result becomes a source for the trust head and is copied out as one draft. A result is fully supported by construction, so the support check never fires on it. Low slot confidence blocks execution and the turn falls back to text.
Evidence
GSM8K: templates copied at 42–45% on stored problems while operation choice stayed at 0–2% at every size and depth, so choosing, not filling, is the failure; Phase 12 composed programs 98%; V1 at 100% when the program was right; the calculator already confirms steps. The parse from open language was V1's failure, and here the parse is retrieval plus copy, trained on open text.
Interface
programs.match(question, hits) → [(pattern_id, slots: [(name, type)])]; fill(slots, pointer) → values, confidences; execute(program, values) → result_codes | error.
Training
Programs give ground truth for free: unlimited question–program–answer traces are generated by executing programs over synthetic worlds, as V1's test worlds were, then reworded through the dense key's neighbours and the rewording data. Verified practice therefore has a perfect checker for this tier. Stage 2 trains slot pointing; stage 3 trains pattern choice on the traces.
Failure modes
Coverage: only what has a program is exact; everything else goes to the network, so this raises the floor on structured questions and is not a general reasoner. Wrong pattern retrieved: exact and wrong, so the gate and reranker matter here as much as for text. Slot errors: handled by confidence; measured as a separate error class.
Open research
How large a program library a 100–300M model can choose from before pattern choice degrades; whether patterns should be retrieved by the question's dense key or by a learned "program key"; composing two programs in one turn; when to add the arithmetic library (math line).
Decides
Exact rate on a structured-question set (dates, counts, state, consistency) against the network alone; pattern-choice accuracy; slot error rate; refusal precision on questions with no program.

4. Software architecture

One process per chat engine; retrieval and encoding on CPU threads; one GPU stream for generation; a second for the dense encoder and reranker so they overlap with decoding of the previous turn. Every module has one job, one interface, and a test that compares it with the eager reference implementation, as the graph step is tested today.

5. Using the hardware fully

The machine is an RTX 3090 (24 GB, bf16 tensor cores), 22 cores / 44 threads, 64 GB RAM. The measured bottleneck at our sizes is kernel launches, not arithmetic, so the design keeps the GPU doing few, large, pre-recorded jobs and gives every scalar job to the CPU.

5.1 Why these choices

  • Graphs over kernels. The profile showed about 300 launches per code and the arithmetic a small part; the graph removed 85% of the time. Low-bit kernels cannot help a launch-bound model, so they are not in the design until the core is large enough to be bandwidth-bound (around 300M).
  • Two GPU streams. The dense encoder and reranker are batched jobs; on their own stream they overlap with the previous turn's decoding and never stall it.
  • CPU does every scalar job. Hashing, indices, span masks, the support check and dialogue state are microsecond jobs on a core; on the GPU each would be a launch.
  • Training keeps the GPU full. Window sampling and mixing on worker threads into pinned memory, bf16 autocast, a fused optimiser and eval on a side stream; the cost meter reports watts so under-utilisation is visible in the ledger.
  • Resumable everything. Warmup-stable-decay means a 100–300M run can train across several nights without restarting; chains skip finished steps; checkpoints save before scoring.

6. Training pipeline

S1
Language and reading. The curated mix (books, Wikipedia, web, conversation, evidence pairs, rewordings), modern block, 100–300M, bf16, the session-20 optimiser and schedule, trained long and resumable. Windows contain evidence followed by the text it supports, so reading is learned in stage 1.
Decides: report card (fluency, evidence gain, reword recall).
S2
Retrieval-augmented Q&A and dialogue. Windows are built by the real cascade (dense retrieval in the loop): the retrieved exchange or passages, with their confidence tags and the confidence fed to the trust head, then the question and answer; 30% of self windows show the right answer under a reworded question (the adopted recipe, sessions 23 and 25); bad evidence (nothing, a wrong exchange) is added once the confidence input is on, since without it the two lessons cancel; multi-turn windows from dialogue threads with the loss on assistant turns; rehearsal of stage-1 text at 30%. Core at a gentle rate, heads at full rate, answer-only loss, end code.
Decides: Q&A groups (stored, added, reworded, new, alone), wrong-evidence test, multi-turn probe.
S3
Verified practice (reasoning). Thinking traces and SEARCH requests sampled on tasks with checkers (reading exact match, multi-hop, dialogue consistency); only confirmed traces are trained on; adapters and heads, core frozen or gentle.
Decides: multi-hop exact match, refusal precision, chat probe reasoning section.
S4
Preference tuning. DPO on better/worse answer pairs for tone, brevity, staying on topic and stopping; pairs built from the probe transcripts and the practice traces.
Decides: chat section of the probe, human grading notes.
S5
Consolidation (continuous). Frequently used memory entries trained into the learned layer and domain adapters at low rate with rehearsal, in idle time.
Decides: added-fact accuracy after consolidation; stored accuracy unchanged.

8. Risks and honest limits

Combining several passages into one answer still needs network size. Everything up to 50M says the small core copies and reads one thing at a time. The 100–300M target is a hypothesis to be tested at three points, not a promise.
The dense encoder and any instruction data are outside knowledge. They are used in retrieval and in tuning, never as the generator; every result that uses them is labelled, and an in-domain key is planned.
Thinking codes can drift. A small model given room to think may wander; the budget is small, the traces are verified, and the support check runs after. Drift is measured, not assumed away.
Speed claims are per code on an idle GPU with replies byte-identical to the eager loop. Any change to that protocol is stated.
What is already certain. Exact memory, instant teaching, retrieval-trained copying, the graph decoder, bf16 training with int8 weights, and the cost ledger are built and measured. The hybrid adds the pieces around them in an order where each step is scored before the next.

10. Reconstruction: pseudocode for every key part

Enough to rebuild the system from scratch without the repository. Python-like, with shapes in comments. Constants: V vocabulary (8,192), D width, L layers, H heads, C window in codes. Special codes: EOS end of answer, SEP blank line, THINK/END, SEARCH, and one confidence-tag code per bucket. All training in bf16 autocast with fp32 weights; all scoring in fp32.

10.1 Compiler

fit_dictionary(texts, size=8192):
    count every whitespace word and every word piece (2..8 bytes) in the training text only
    keep the top `size - 256 - specials` units by (count x bytes saved); add 256 byte-fallback codes and the specials
    assign ids deterministically (sorted by count then bytes); hash the table -> dictionary id

encode(text):                       # greedy longest match, left to right; byte fallback never fails
    i = 0; out = []
    while i < len(text):
        unit = longest dictionary entry that prefixes text[i:]   (trie lookup)
        out.append(id[unit] if unit else BYTE_BASE + text[i]); i += len(unit) or 1
    return out                      # decode(out) == text, always

key(question):                      # the memory key: content words only
    return frozenset(w for w in words(lowercase(question)) if w not in STOP and len(w) > 1)

10.2 Memory tiers and the duplicate check

class MemoryStore:
    exact: dict[frozenset, id]      # question key -> entry
    entries: list[(kind, question_bytes, payload_bytes, source, time)]   # kind in {pair, passage, session}
    inverted: dict[word, list[id]]; df: Counter[word]
    dense: Matrix[N, 384] fp16      # unit vectors from the dense key (3.3); appended on every add

    add(kind, question, payload, source):
        k = key(question)
        if k in exact and same_text(entries[exact[k]].payload, payload): return DUPLICATE(exact[k])
        if k in exact: replace entries[exact[k]].payload; log conflict; return REPLACED(exact[k])
        cands = candidates(question, 20)                  # ms, see below
        best = max(cands, key=score) if cands else None
        if best and best.lexical >= 0.9 and overlap_f1(best.payload, payload) >= 0.8: return DUPLICATE(best.id)
        if best and 0.5 <= best.lexical < 0.9 and engine.answers_correctly(question, payload): return DUPLICATE(best.id)
        i = len(entries); entries.append(...); exact.setdefault(k, i)
        for w in k: inverted[w].append(i); df[w] += 1
        dense = vstack(dense, dense_key.embed(question))
        return STORED(i)

    candidates(question, k):                               # lexical half of the cascade
        words = sorted(key(question), key=lambda w: df[w])[:3]   # rarest words select the candidates
        pool = union(inverted[w] for w in words if df[w] <= 0.05 * len(entries))
        lex = {i: sum(idf(w) for w in key_i & key_q) / sum(idf(w) for w in key_i | key_q) for i in pool}
        return top k of lex

10.3 Retrieval cascade

retrieve(question, history, k=3):
    if key(question) in exact: return [Hit(exact[key], lexical=1.0)]        # stage 1, exact: answer verbatim
    q_lex  = top50 of candidates(question, 50)                                # stage 2, hybrid
    q_den  = top50 by cosine(dense_key.embed(question), dense)
    pool   = q_lex | q_den
    hybrid = {i: lex.get(i, 0) + W_DENSE * cos[i] for i in pool}           # W_DENSE fitted on held-out rewordings (2.0)
    top10  = top 10 of hybrid
    rerank = {i: cross_encoder(question, entries[i].question + entries[i].payload) for i in top10}   # stage 3
    hits   = [Hit(i, tier, lex[i], cos[i], rerank[i]) for i in top10 sorted by rerank]
    return gate(hits, k)                                                     # stage 4

gate(hits, k):                      # learned; a 2-layer net on (lexical, dense, rerank, model_size) -> use/none
    keep = [h for h in hits if gate_net(h.scores) > 0.5]
    return keep[:k]                 # may be empty: the generator then answers alone, and the support check decides

10.4 Context builder

build(turns, hits, question, budget=C, think_budget=96):
    ev = []
    for h in reversed(hits):                                # best evidence nearest the question
        ev += [TAG[bucket(h.rerank)]] + encode(render(h)) + [SEP]
    hist = []
    for t in turns[-2:]: hist += encode("User: " + t.user + "\nAssistant: " + t.reply) + [SEP]
    if len(hist) + len(ev) + len(q) + think_budget > budget:
        hist = encode(extractive_summary(turns)) + [SEP]        # entity facts + last answers; never generated
    older = retrieve(question, scope=session)               # earlier turns by content, as evidence
    codes = hist + ev + encode("User: " + question + "\nAssistant:")
    spans = {source i: positions of its codes}              # the copy pointer may point only inside spans
    conf  = {source i: (lexical, dense, rerank)}
    return Context(codes, spans, conf, think_budget)

10.5 Generator core

class Block:                        # modern block, pre-norm
    forward(x):                     # x: (B, T, D)
        q, k, v = split(Wqkv @ rmsnorm(x)); q, k = rope(q), rope(k)   # grouped-query: Hkv < H heads for k, v
        x = x + Wo @ attention(q, k, v, causal)
        return x + Wdown @ (silu(Wgate @ rmsnorm(x)) * Wup @ rmsnorm(x))   # SwiGLU, inner = 8D/3

class MemoryLayer:                  # product-key memory, after block L/2
    keys: two tables of sqrt(N) half-keys (D/2 each); values: Embedding(N, 128); up: Linear(128, D)   # N = 256k..1M
    forward(x): q = Wq @ x; top-k over cartesian product of half-key scores (k=32); return x + up(sum softmax(s) * values[idx])
    # value width 128 keeps the tier at 33-130M parameters (int8 at rest); full-width values would be billions

class Core:
    hidden(codes):                  # (B, T) -> (B, T, D)
        h = E[codes]; for i, b in enumerate(blocks): h = b(h); if i == L//2: h = memory_layer(h)
        return rmsnorm_f(h)
    logits(h): return h @ E.T       # tied output
    mtp_heads: 2 small heads predicting codes t+2, t+3 from h (training loss + drafts)

10.6 Trust head and copy pointer (one position)

mix(h_last, ctx, sources):          # h_last: (D,) ; returns log-probabilities over V
    p_net  = softmax(h_last @ E.T)
    # copy pointer: attend over the window's states where spans allow; probability mass goes to the follower code
    s      = (Wq_copy @ h_last) . K_last[j] / sqrt(D)  for j < t and j in allowed spans   # K_last: the last block's attention keys, reused
    a      = softmax(s); p_copy = scatter_add(zeros(V), next_code[j], a[j])
    p_mem  = softmax(memory_layer.readout(h_last))              # optional direct readout of the learned tier
    p_prog = one_hot(program_result_code) if a program ran else zeros(V)
    conf   = [max a, entropy(a), lexical, dense, rerank, gate]  # retrieval confidence enters here
    w      = softmax(Wmix @ concat(h_last, conf))               # weights over (net, copy, mem, program)
    return log(w . [p_net, p_copy, p_mem, p_prog] + 1e-9)       # computed in fp32

training loss (stage 2) = -log mix(...)[target] on answer codes only
    30% of windows carry bad evidence: a distractor (10%), nothing (10%), or two conflicting pieces with different tags (10%)
    the gate is trained on the same windows with the target "did using the evidence lower the answer loss?"

10.7 Decoder: graph step and copy-as-draft

buffers (fixed, on GPU): win[C] codes, K[L][H][C][d], V[L][H][C][d], states[C][D], copy_keys[C][D], spans[C], pos scalar

graph_step(code, p):                # recorded once with torch.cuda.graph, replayed per code
    win[p] = code; h = E[code] (+ rope by p inside attention)
    for l in blocks: K[l][:, p], V[l][:, p] = project(h); h = block_l(h, K[l][:, :p+1], V[l][:, :p+1]); states[p] = h
    copy_keys[p] = Wk_copy @ h
    return mix(h, win, spans)        # logits for position p+1

evidence_cache[id] = (K_unrotated[L][H][n][d], V[L][H][n][d])    # computed once per passage, stored int8 on disk / fp16 in RAM

prefill(ctx):
    for each evidence span e at slot s: K[l][:, s:s+n] = rotate(evidence_cache[e].K, by positions s..s+n); V likewise   # no recompute
    run the history + question codes eagerly (the only new tokens); logits = mix(last state)

answer(ctx, max_codes):
    prefill(ctx); p = len(ctx.codes); out = []; unsupported = 0
    while len(out) < max_codes:
        c = argmax(logits masked by never-seen codes and repeat blocking)
        if c == EOS: break
        out.append(c)
        if is_content(c) and not (w.copy >= 0.5 or w.program >= 0.5 or p_net[c] >= 0.6): unsupported += 1
        if unsupported > SUPPORT_LIMIT: break                 # early stop: the support check runs inside the loop
        if a program fired: draft = result_codes            # one draft, fully supported
        elif copying (w.copy > 0.5): j = pointer target; draft = win[j+1 : j+1+k]   # any span: answer, passage, earlier turn
        else: draft = mtp_heads(h)                            # 2 codes from the multi-token heads
        logits_k = graph_verify(draft, p)                     # one batched replay over k positions
        accept the longest prefix where argmax(logits_k[i]) == draft[i]; append; p += accepted
        logits = logits_k[accepted] if accepted < k else graph_step(draft[-1], p)
    return out, per-code source weights w

10.8 Reasoning: thinking codes, self-requested search, support check

turn(question, session):
    hits = retrieve(question, session.turns)
    if hits and hits[0].lexical == 1.0: reply = entries[hits[0].id].payload; store(session, question, reply); return reply, sources=[hits[0].id]
    prog = programs.match(question, hits)                        # program tier: exact where a pattern fits
    if prog and (values, conf := fill(prog.slots, pointer)) and min(conf) >= 0.8:
        result = execute(prog, values)
        if result is not error: reply = render(result); store(session, question, reply); return reply, sources=[prog.id] + slot sources
    ctx = build(session.turns, hits, question)
    think = not (hits and gate_confident(hits[0]))                # adaptive: confident matches skip thinking
    for attempt in range(2):
        codes, w = answer(ctx + ([THINK] if think else []), max_codes=(think_budget if think else 0) + answer_budget)
        hops = 0
        while SEARCH in codes and hops < 2:                      # the model asked for evidence mid-thought; two hops at most
            hops += 1; query = decode(codes after SEARCH up to END)
            more  = retrieve(query, session.turns); ctx = insert(ctx, more); codes, w = resume(ctx, codes)
        thought, reply = split(codes, END)                       # thought is never shown
        verdict = support_check(reply, w, ctx)
        if verdict.ok: break
        ctx = insert(ctx, retrieve(reply_as_query(reply)))       # one more search, then give up honestly
    if not verdict.ok: reply = "I don't know. The closest I have: " + decode(entries[hits[0].id].payload) if hits else "I don't know."
    learner.write_back(session, question, reply, verdict); return reply, verdict.sources

support_check(reply, w, ctx):
    content = [i for i, c in enumerate(reply) if is_content_word(c)]
    supported = [i for i in content if w[i].copy >= 0.5 or w[i].tool >= 0.5 or w[i].net_prob >= 0.6]
    share = len(supported) / max(1, len(content))
    return Verdict(ok = share >= THRESHOLD[core_size], sources = {evidence id of each copied code}, share)   # fitted per size on known-unanswerable questions

stage-3 training (verified practice): for task in (reading EM, multi-hop EM, dialogue consistency, program traces):
    sample 4 answers with thinking at temperature 0.7; keep those whose answer the checker confirms; fine-tune heads + adapters on them
    loss on THINK..END codes only from kept traces (never from unverified ones)

10.8b Program tier

ProgramEntry = (pattern: question text with slot markers, slots: [(name, type)], program: [op, ...], executor)
    types: entity, attribute, number, date, duration, unit, list, text
    ops (typed, exact, CPU): set(entity, attr, value) · add(entity, attr, delta) · get(entity, attr) · count(list, pred)
                            compare(a, b) · date_add(date, duration) · date_diff(a, b) · convert(value, unit, unit)
                            find(tier, pred) · filter(rows, pred) · join(rows, rows, key) · check(fact, rows)
    the September event row (kind, A, B, value, active) is set/add/get over entity state

programs.match(question, hits): candidates = [h for h in hits if h.tier == program][:3]   # retrieved like any entry
fill(slots, pointer):   for each slot: j = pointer over question + evidence spans restricted to the slot's type; value = parse(type, span j); conf = max attention
execute(program, values): run ops in order on a fresh state seeded from the session's typed facts; return rendered result or error

synthetic traces (unlimited, verified): world = random entities/attrs/dates; program = random short op list; question = template(program) reworded
    through the rewording data; answer = execute(program, world)  ->  (question, pattern, slots, answer) for stages 2 and 3

10.9 Learning that never stops

write_back(session, q, reply, verdict):
    session_store.add(q, reply)                                  # always
    if verdict.ok and verdict.share >= 0.9: memory.add(pair, q, reply, source="self", via duplicate check)
    for fact in user_stated_facts(q): memory.add(pair, fact.question_form, fact.answer, source="user")

practise(budget_s):                 # idle time, low priority, stops when a chat starts
    for q, gold in sample(passage_tier questions with known answers):
        traces = [turn_with_thinking(q) for _ in range(4)]; keep = [t for t in traces if checker(t.reply, gold)]
        train(heads + adapters, keep, lr=1e-4, rehearsal=0.3)

consolidate(budget_s):
    hot = entries used >= 5 times this week
    train(memory_layer + domain adapters, windows built from hot, lr=1e-5, rehearsal=0.3)   # core frozen
    archive entries unused for 90 days (never delete)

10.11 Hardware schedule

answering (one process):
    CPU threads: encode/decode, exact hash, inverted index, context packing, support check, dialogue state
    GPU stream 0: prefill (eager, once) then graph replays; stream 1: dense encoder + reranker for the next likely query
    buffers pinned; the only per-code host transfer is the chosen code

training:
    N worker processes build windows into shared pinned memory (random windows for prose; aligned for structured units)
    GPU: bf16 autocast, flash attention, fused optimiser step, eval every 300 s on a side stream, checkpoint before scoring
    power sampled every 2 s -> joules per step in the result; utilisation target >= 90%
    warmup-stable-decay: a run can stop at any step in the flat phase and resume the next night

The through-line. From the September semantic compiler to this design, one principle has held: keep exact what can be exact, and learn only the boundary with language. The first attempt placed the boundary at a hand-written grammar and could not leave it. This design places it inside a small trained network with memory on both sides, and brings the exact machinery back as a retrievable program tier.
